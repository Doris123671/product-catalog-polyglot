This assignment was a practical introduction to polyglot persistence, which is the idea of using more than one database system together so each one can handle the workload it fits best. MongoDB was the most natural choice for the product catalog because it stores documents with flexible fields such as tags and ratings. That flexibility made the seed data easy to model and helped demonstrate how a catalog can evolve without changing the entire schema. Redis was especially interesting because it is optimized for fast, in-memory operations. Its ability to cache values, maintain sorted sets for rankings, and support live pub/sub messages showed how it can improve responsiveness in applications that need low-latency data access.

PostgreSQL with pgvector added a different dimension by enabling semantic search. Instead of searching by exact keyword only, it allowed the system to compare vector embeddings and find products that are conceptually similar. That was a valuable reminder that not every data problem is best solved with a traditional relational model alone. In practice, I would choose MongoDB when I need a flexible document store for catalogs or content-heavy data, Redis when I need fast temporary state such as caching or leaderboards, and PostgreSQL when I need relational consistency, analytics, or vector-based similarity search.

The most interesting part of the project was seeing how these technologies complement one another rather than compete. A product catalog can live in MongoDB, be accelerated by Redis, and enriched with semantic discovery through PostgreSQL and pgvector. This made the architecture feel much more realistic and showed why modern applications often combine multiple database technologies under one system design.
